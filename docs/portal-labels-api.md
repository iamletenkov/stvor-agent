# Контракт `GET /robot-api/v1/labels`

Что должен отдавать портал, чтобы `stvor-agent` применял на машине метки узла Teleport `space` и `env`.
Контракт — версия 1, тот же, что у `bisquite-teleport-agent` 3.x: со стороны портала в 4.x ничего не
меняется. Агент проверяет ответ строго, и любое отличие формы — отказ без записи.

Портал — любой сервис, который знает, в каком пространстве (`space`) и окружении (`env`) должна быть
машина. Пример реализации — портал Stvor. Реализация клиента — `internal/portal` (запрос и разбор),
`internal/reconcile` (что агент делает с ответом).

## Включение на машине

```sh
read -rs T && printf '%s' "$T" | sudo stvor-agent enable URL=https://<портал>/robot-api/v1/labels; unset T
```

- Адрес — ровно `https://<хост>[:порт]/robot-api/v1/labels`
  (`^https://[a-z0-9.-]+(:[0-9]{1,5})?/robot-api/v1/labels$`); другой путь, `http://`, заглавные
  буквы или кавычка в адресе — отказ.
- Токен — 43 знака `[A-Za-z0-9_-]` (32 байта в base64url без `=`), читается со stdin; пробелы и
  перевод строки по краям отбрасываются. Токен выдаёт портал на одну машину; повторный `enable` с новым
  токеном — перевыпуск, с другим адресом — ещё и сброс запомненного ответа.
- Токен и адрес лежат вместе в `/etc/stvor-agent/token` (0600, root, каталог 0700): строки `url=…` и
  `token=…`. Токен уходит только на этот адрес; в argv, окружение дочерних процессов, `status` и журнал
  он не попадает.

## Запрос

Служба `stvor-agent.service` опрашивает портал раз в `STVOR_AGENT_INTERVAL` секунд (60 по умолчанию,
60–600) плюс случайные 0–20 с; первый опрос — через 0–20 с после старта. Разово — `stvor-agent sync`.

```
GET <url из файла токена>
  Authorization: Bearer <токен>
  If-None-Match: "<ревизия>"        # если ответ уже запомнен; ревизия в кавычках
  X-Applied-Revision: <ревизия>     # только вместе с If-None-Match той же ревизии
  User-Agent: stvor-agent/<версия>  # справочно, портал его не читает
```

- `HEAD` агент не шлёт. Заголовок `ETag` ответа агент не читает: `If-None-Match` строится из `revision`
  тела, то есть портал должен считать ETag ответа равным `"<revision>"` и сравнивать `If-None-Match` с
  ним.
- `X-Applied-Revision` уходит, только когда ревизия действительно действует: управляемые метки
  расширения `teleport` равны ожидаемым, маркера незавершённого перезапуска нет, узел зарегистрирован,
  агент Teleport активен, и ревизия уже отмечена применённой. Портал узнаёт о применении на следующем
  опросе после него и по нему может завершать перенос машины между пространствами.
- Только `https`, TLS ≥ 1.2, системные корни; прокси — `HTTPS_PROXY` из окружения службы (drop-in,
  [README](../README.md#прокси)). Редиректам агент не следует. Тайм-ауты: соединение и TLS — 10 с,
  весь запрос с телом — 30 с.
- Лимит портала — 6 запросов в минуту на значение `Authorization`: поэтому интервал не меньше 60 с и
  агент никогда не повторяет запрос раньше своего тика.

## Ответ

| Код | Тело | Что делает агент | Следующий опрос |
|---|---|---|---|
| `200` | `{"labels":{"env":"<v>","space":"<v>"},"revision":"<16 hex>"}` | проверяет тело целиком, запоминает, применяет | через интервал |
| `304` | не читается | ничего не скачивает; сверяет метки с запомненным ответом | через интервал |
| `304` без запомненного ответа | — | строка в журнале, ничего не тронуто | через интервал |
| `401` | не читается | строка в журнале, ничего не тронуто | через 600 с (ускоряет только `enable`) |
| `429`, `3xx`, `5xx`, прочие коды, сеть, TLS, тайм-аут | не читается | строка в журнале, ничего не тронуто | backoff: `min(интервал · 2^min(n,3), 600 с)` |
| `200` с телом не по контракту | не логируется | строка в журнале (`bad_body`), ничего не тронуто | backoff |

`n` — число неудач подряд; `200` и `304` его сбрасывают. Тела `401` и любых ошибок агент в журнал не
пишет. У `stvor-agent sync` ошибка сети или HTTP — код 0 (служба повторит), тело не по контракту — код 1.

Тело `200` — JSON с ключами **ровно в этом порядке**, каждый один раз:

```json
{"labels":{"env":"prod","space":"sp-1a2b3c4d"},"revision":"0123456789abcdef"}
```

- `env`, `space` — `^[a-z0-9][a-z0-9-]{0,62}$` (алфавит метки DNS: в значение не пролезают кавычка,
  запятая, `=` и перевод строки);
- `revision` — `^[0-9a-f]{16}$`, меняется при любом изменении меток;
- тело не длиннее 4096 байт, валидный UTF-8, без NUL и без экранирований `\` (законному ответу они не
  нужны);
- пробелы между токенами допустимы, но лишние ключи, вложенные объекты сверх `labels`, повтор ключа,
  иной регистр ключа (`"ENV"`) и что-либо после объекта — нет.

Разбор идёт по токенам `encoding/json` (не `Unmarshal`, который принимает повтор ключа и сопоставляет
ключи без учёта регистра). Любое отклонение — отказ, ничего не записано.

## Что агент делает с ответом

- Значения уходят в расширение `teleport` каталога cream как **управляемые метки**
  (`cream run teleport set-managed env=<v> space=<v>`, ручка `TELEPORT_MANAGED_LABELS`). Они
  перекрывают одноимённые метки оператора (`TELEPORT_ENV`, `space=` в `TELEPORT_LABELS`), которые сами
  не меняются.
- Изменение применяется **одним перезапуском** `teleport.service` (не HUP) с подтверждением нового
  запуска: узел и все его веб-приложения переезжают в новое пространство вместе, открытые SSH-сессии
  прежнего пространства рвутся. Если итоговый `teleport.yaml` не меняется (первый опрос после `join`,
  который уже записал те же `env`/`space`), перезапуска нет.
- Сверяется состояние, а не ревизия: на каждом опросе (и на `304`) метки в `teleport` сравниваются с
  последним ответом портала; расхождение (незавершённый перезапуск, неактивный агент Teleport, чужой
  перезапуск) исправляется.
- После трёх неподтверждённых перезапусков подряд, пока агент Teleport активен, служба перезапускает его
  не чаще раза в 15 минут. `stvor-agent sync` и `apply` паузой не ограничены.
- Узел ещё не зарегистрирован — метки записываются без перезапуска и начинают действовать после `join`.

## Чего портал сделать не может

- Доставить код на машину: агент принимает только два значения из фиксированного алфавита и передаёт
  их аргументами без shell.
- Поменять кластер, регистрацию, приложения и прочие метки: агент передаёт в `teleport` ровно ключи
  `env` и `space`.
- Задать метки `app`, `os_logins`, `teleport.icon`, `stvor_agent`.

Портал при этом — источник правды о доступе: сменив `space`/`env`, он переносит машину между
пространствами, и роли кластера дают доступ по новым меткам.

## Признак агента на узле

С 4.0.0 узел несёт **динамическую** метку `stvor_agent=<X.Y.Z>`: Teleport раз в 5 минут исполняет
`/usr/bin/stvor-agent version --label` и публикует вывод (в инвентаре — `cmd_labels` узла). Агент
выключен (`stvor-agent disable`, нет файла токена) — значение пустое. Метку включает обёртка
`stvor-agent` каталога cream drop-in-файлом `/etc/cream/teleport/command-labels.d/stvor_agent`.
Обновление агента меняет значение без перезапуска агента Teleport. Метка — часть контракта и не
переименовывается.

Агент 3.x вместо неё ставил статические метки `managed_by=bisquite-teleport-agent` и (с 3.0.1)
`bisquite_agent_version=<X.Y.Z>`. Портал распознаёт агента по `stvor_agent` **или** по старой
`managed_by`, пока на машинах остаётся 3.x.
